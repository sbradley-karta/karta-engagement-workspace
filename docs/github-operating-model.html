Engagement Delivery Workspace

One organization, one main branch, and the three places main flows to

Will and Paul approved a Karta-owned GitHub organization and Google Cloud account on September 9. This page shows how the codebase is organized once both exist, how a change travels from a branch to a live engagement page or a deployed service, and which guardrails hold it together.

The shape of it

People work through the organization, never around it. Everything that reaches a member, an engagement page, or the service starts as a commit on main.

The life of one change

Whether the change is a page fix, a schema field, or a new assembler rule, it takes the same path. Only the last step differs by what changed.

First week after the organization exists

Move, about an hour

  1. Create the empty repository karta-engagement-delivery-workspace in the organization
  2. git remote add origin … then git push -u origin main from the local repository
  3. Confirm GitHub Actions ran green on the first push
  4. Archive the personal repository and remove the legacy remote
  5. Create karta-claude-skills and move the skills in with history

Protect and organize

  • Protect main: pull requests required, one review on service paths, CI required, no force pushes
  • Enable two-factor enforcement and secret scanning on the organization
  • Create the labels and file the backlog as Issues: deck fidelity refactor, Entra switch, Ethan's contract review, Gate 7 access test
  • Tag v0.2.0 at the Gate 6 close so the pilot has a named baseline
  • Later, when the Google Cloud transfer is done: add the deploy job that runs from main
