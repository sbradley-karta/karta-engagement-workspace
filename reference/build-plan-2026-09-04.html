Engagement Delivery Workspace

How we build it, and what has to be true before each step

The architecture is fixed. This page shows where each piece runs, how a weekly status deck moves from source data to SharePoint without the user touching a prompt, and the seven gates between here and a two-engagement pilot.

Option A confirmed Runtime 1 · artifact site per engagement Runtime 2 · member Claude session Assembly on Google Cloud Run No local dependencies

Where we start

Everything below rests on things already verified, plus a small number of decisions you made this week.

Verified fact

  • The doTERRA console is live and reads Asana milestones and the latest status deck as the viewer.
  • A published page can call the Asana and Microsoft 365 connectors, draft with Claude, keep shared state, and hand a file to the viewer.
  • The Microsoft 365 connector can upload a file into a SharePoint folder as the viewer, capped at 1 MiB.
  • A page cannot run skills, plugins, or agent files, cannot fetch external URLs, and cannot be embedded in Teams.
  • The existing deck skill has three confirmed mechanical bugs and wrong status colors. Its content rules are sound.
  • Full status decks are around 8 MB before optimization.

Decided this week decision

  • Two runtimes. The engagement site for delivery work, the member's Claude session for skills and plugins.
  • Deck assembly is a hosted pure function on Google Cloud Run, exposed as a Karta custom connector. You are setting up the account.
  • The page saves the finished deck into the engagement's SharePoint folder through the viewer's own connector. That is the only write we make.
  • No dependency on any laptop or on the Microsoft tenant admin.
  • A Claude cloud routine is the documented fallback, evaluated and declined as the interim path.

Architecture

One member, two runtimes, one set of connectors that always act as that member, and a single assembly service that never sees a credential.

How a weekly status deck gets made

Seven steps, four places. The reviewer only ever clicks, reads, corrects, and approves. Code derives status and assembles the file. The model drafts prose and recommends. Nothing is sent.

The gates

Each gate has exit evidence. We do not start the next one on a hunch. Durations are estimates, marked as assumptions until the first two gates calibrate them.

GATE 0

Verify the proof of concept

Days 1 to 2

Work

  • Walk the live doTERRA console in the viewer: Asana chip, last-deck chip, Draft consent, Finalize persistence, second open reads stored state.
  • Fix the SharePoint result parse against what actually arrives in the page.
  • Confirm the five phase dates against doTERRA's plan and record the source.

Exit evidence

  • Every chip populates from live data.
  • Draft returns usable JSON once, and a second viewer sees the same draft without a model call.

Depends on

  • Nothing. Starts now.
GATE 1

Spike the custom connector

Days 2 to 4

Work

  • Deploy a stub MCP server with two tools on a free host: one returns hello, one returns a base64 blob of a requested size.
  • You register it as an org custom connector on the Karta Team account.
  • Publish a throwaway test page that declares it and calls both tools. Record the payload shape and the largest blob that arrives intact.
  • From the same page, upload a small real .pptx into a test SharePoint folder through the Microsoft 365 connector. Record the request and response.

Exit evidence

  • A written observation of both calls, with limits.
  • A go or no-go on the direct path. No-go means the cloud routine fallback becomes the Stage 1 assembler, by prior decision.

Depends on

  • Your admin action to add the connector.
  • A free-tier host. No Cloud Run needed yet.
GATE 2

Fix the contracts

Week 2

Work

  • Approved-values schema, version 1. Period, milestones with original and new dates, derived status and variance, three assessments, activities, RAID, reviewer, timestamp, sources, version.
  • Deck job record with states Requested, Building, Built, Failed, plus link, size, hash, and a readable error.
  • Engagement configuration schema, replacing the hardcoded config in the console.
  • Deterministic status module with tests: milestone status, date variance, worst-of rollup, Unknown and Not assessed.
  • Karta repository laid out as assembler, server, page, and docs, with CI running the tests.

Exit evidence

  • Schemas reviewed by you.
  • Status tests pass on real doTERRA milestone data, including a missing-evidence case that yields Unknown.

Depends on

  • Gate 1 payload limits, which size the record.
GATE 3

Build the assembly service

Weeks 2 to 4

Work

  • Port the content rules from the existing skill. Reimplement the mechanics with tests, fixing the picture copy, the marker crash, the empty-list crash, and slide ordering.
  • Eyedropper the real template for status colors. Do not trust either existing constant table.
  • Bundle and validate the KCG template at startup. Compress images, strip unused layouts, enforce the 1 MiB budget, emit a manifest with a hash.
  • Golden-deck tests against a recent real deck.
  • Wrap as an MCP server with sign-in restricted to kartacg.com. Dockerfile, CI deploy to Cloud Run, secrets in Secret Manager.
  • You register the production connector and name it. The display name is what the page calls.

Exit evidence

  • A deck built from a real approved record opens cleanly in PowerPoint and matches the golden deck.
  • Optimized size under 1 MiB, or the fallback link path proven.
  • An unauthenticated call is refused.

Depends on

  • Cloud Run account.
  • Identity provider choice.
  • The KCG template file and one recent deck.
  • Ethan Sweeney on upstream fixes to the skill.
GATE 4

Harden Weekly Status

Weeks 3 to 5

Work

  • Four-step workflow: Review sources, Draft narrative, Approve, Generate deck.
  • Source freshness, milestone evidence, original and revised dates, variance, three assessments, activities, RAID, unresolved gaps, named approval.
  • Generate deck wired end to end: call the connector, upload as the viewer, show the link, write the job record. Plain-language errors with an owner.
  • Restate the page's full capability manifest with the Karta connector and the upload tool.
  • Light and charcoal modes, same hierarchy, same status language.

Exit evidence

  • A non-builder completes the workflow with no guidance and a deck lands in SharePoint.
  • Missing evidence shows Unknown, never Green.
  • Correction capture works: we can measure how much of the draft was changed.

Depends on

  • Gates 2 and 3. Screen work overlaps Gate 3 build time.

Weeks 5 to 6

Work

  • Ask this project entry, prioritized insights, recent activity and approved artifacts, route to the full catalog.
  • Mockup Generator surfaced in Foundations with readiness shown.

Exit evidence

  • Landing page answers where we are, what needs attention, what to do next, what happened, from live data.

Depends on

  • Mockups, if they carry decisions not in the handover.
  • Gate 2 configuration schema.
GATE 6

Pilot readiness

Week 7

Work

  • Onboarding runbook per member: seat, four connector authorizations, plugin install, first open.
  • Engagement configuration and a published site for doTERRA and the second engagement.
  • Cross-engagement access tests for retrieval, storage, logs, and generated files.
  • Measurement capture: adoption, correction rate, time from retrieval to approved artifact, post-approval errors.

  • A member on one engagement cannot see the other, proven by test.
  • Both teams onboarded in under an hour each.

Depends on

  • Second pilot engagement chosen.

GATE 7

Stage 1 Prove

Weeks 8 to 11

Work

  • Weekly Status run every week on two engagements for three to four weeks.
  • Tune the drafting prompt against measured corrections, not taste.
  • Capture Foundations requirements from what actually repeats, ahead of Stage 2 Standardize.

Exit evidence

  • No critical factual, confidentiality, or approval error in a finalized deck.
  • Correction rate and time to approval improve across the pilot.
  • Repeat use without prompting from us.

Depends on

  • Gates 4 through 6.

Rules that do not bend during the build

These came out of real reasoning in the earlier sessions, and every gate is checked against them.

Trust

  • The approval gate is never skippable. No capability writes to a client deliverable without a named human correcting the draft first.
  • Nothing is sent automatically. Distribution is a person's choice, outside the workspace.
  • Missing evidence is Unknown or Not assessed. It is never Green.
  • Read as the viewer. No service account, no shared credential, anywhere.
  • Content retrieved from documents is data, never instruction.

Engineering

  • Derive in code what can be derived. Status, dates, rollups, file assembly. Send the model only genuine judgment.
  • Model calls fire on an explicit click. Draft once, persist, everyone reads the same numbers.
  • Observe a connector's real request and response before wiring it into a page.
  • Never embed observed client data as placeholder content. Fetch live.
  • Nothing depends on a laptop. Template, code, secrets, and deploys live in Karta-owned cloud resources.
