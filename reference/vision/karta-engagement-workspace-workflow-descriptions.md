# Karta Engagement Delivery Workspace

## Workflow Descriptions

**Status:** Supporting reference for the workflow inventory  
**Date:** September 6, 2026  
**Purpose:** Explain each workflow in plain language for a reader with no prior product or project context

| Lifecycle area | Workflow | Short description |
| --- | --- | --- |
| Project Planning | Sales Handover | Transfers the client relationship, sales history, proposed use case, demonstrations, expectations, and agreed commitments from the sales team to the delivery team. |
| Project Planning | Delivery-Team Handover Acceptance | Records that the delivery owner has reviewed the sales handover, resolved material gaps, and accepted responsibility for starting the engagement. |
| Project Planning | Client and Company Brief | Gives the project team a concise introduction to the client, its business, the relationship with Karta, the business problem, and the expected value of the project. |
| Project Planning | Stakeholder Mapping | Identifies the people who influence, approve, use, or support the solution and explains their roles, relationships, decision rights, and known concerns. |
| Project Planning | Commercial and Scope Baseline | Captures the approved SOW, deliverables, assumptions, exclusions, budget, schedule, and client responsibilities that define what Karta has committed to deliver. |
| Project Planning | Use-Case Guidance | Provides relevant Karta examples, lessons learned, delivery advice, and likely design considerations for the client's use case. |
| Project Planning | Team Onboarding | Gives each team member the project context, responsibilities, approved materials, and practical guidance needed to begin contributing effectively. |
| Project Planning | Engagement Setup | Configures the workspace for the engagement, including dates, roles, sources, permissions, templates, reviewers, and available capabilities. |
| Project Planning | Source and Access Validation | Checks that the team can reach the required systems and documents and clearly identifies missing, outdated, or incorrectly permissioned sources. |
| Project Planning | Kickoff Preparation | Creates the agenda, presentation, logistics, working expectations, and decisions needed for an effective client kickoff. |
| Project Planning | First-Two-Weeks Planning | Organizes the workshops, data requests, working sessions, deliverables, owners, and decisions required immediately after kickoff. |
| Project Planning | Initial Delivery Plan | Converts the agreed scope into a practical workplan with milestones, sequencing, dependencies, responsibilities, and resource expectations. |
| Project Planning | Data Intake Coordination | Organizes the initial data requests, sample files, owners, due dates, validation steps, and unresolved data gaps. |
| Project Planning | Initial RAID Assessment | Identifies the first known risks, assumptions, issues, and dependencies that could affect delivery. |
| Foundations | Meeting Closeout | Turns meeting notes or transcripts into reviewed actions, decisions, requirements, risks, questions, and follow-up communications. |
| Foundations | Business Requirements | Documents what the business needs the solution to do, why it matters, how success will be assessed, and who approves it. |
| Foundations | Requirements Quality Review | Checks requirements for unclear language, duplication, conflicts, missing evidence, missing acceptance criteria, and incomplete ownership. |
| Foundations | Design Document | Explains how the proposed solution will satisfy the approved requirements, including key design choices, rules, processes, data, and constraints. |
| Foundations | Process Benchmark | Compares the proposed process with relevant leading practices, Karta experience, and prior implementation patterns to identify improvement opportunities. |
| Foundations | Business Process Flows | Shows the steps, roles, decisions, inputs, and outputs in the business process the solution will support. |
| Foundations | Mockup Generator | Produces an editable visual concept that helps the team and client discuss proposed pages, reports, workflows, states, and interactions. |
| Foundations | List and Data Matrix | Defines the lists, dimensions, hierarchies, data elements, source systems, owners, and relationships required by the solution. |
| Foundations | Data Mapping and Gap Analysis | Maps available source data to solution requirements and identifies missing fields, quality concerns, ownership gaps, and transformation needs. |
| Foundations | Solution Architecture | Describes the overall technical design, including solution components, environments, integrations, data movement, security, and important constraints. |
| Foundations | Decision and Assumption Management | Maintains a reviewed record of decisions and assumptions, including their rationale, owner, approval, date, and affected deliverables. |
| Foundations | Design-to-Scope Reconciliation | Compares the emerging solution design with the contracted scope and identifies anything that may exceed, reduce, or materially change the original commitment. |
| Foundations | Delivery Feasibility Review | Reassesses whether the proposed solution can still be delivered with the available time, budget, capacity, skills, and dependencies. |
| Foundations | Scope Classification | Determines whether a new finding is already in scope, a clarification, a design trade-off, a defect, or a requested change. |
| Foundations | Change-Control Preparation | Prepares the facts, options, cost, schedule, delivery impact, recommendation, and approval request needed for a scope decision. |
| Build | Project Build Plan | Breaks the approved solution design into sequenced development work with owners, dependencies, sprint objectives, and expected review points. |
| Build | Requirements-to-Build Traceability | Shows which development items satisfy each approved requirement and identifies requirements that have no build coverage. |
| Build | Data Hub Design and Validation | Defines and checks the structures, mappings, transformations, and data flows used to provide governed data to the solution. |
| Build | Model Configuration Documentation | Records how the solution was configured so another qualified team member can understand, review, maintain, or support it. |
| Build | Dashboard and Report Specification | Defines the purpose, audience, layout, calculations, interactions, filters, and acceptance expectations for each dashboard or report. |
| Build | Security Design Validation | Checks that roles, access, segregation, and data visibility match the approved security requirements and solution design. |
| Build | Build Evidence Capture | Stores proof of what was developed and links that proof to the requirement, design decision, and sprint in which it was reviewed. |
| Build | Configuration Quality Review | Reviews the configured solution against defined Karta development standards, design rules, documentation expectations, and quality checks. |
| Build | Design-Deviation Management | Identifies where the build differs from the approved design and routes the difference for correction, acceptance, or change control. |
| Build | Sprint Review Preparation | Organizes what will be demonstrated, the requirements covered, the evidence available, and the decisions expected during a sprint review. |
| Build | Sprint Review Record | Records what was demonstrated, who attended, the feedback received, the decisions made, and the follow-up work assigned. |
| Build | Initial Business Acceptance | Captures whether an authorized business reviewer initially accepts, conditionally accepts, rejects, or requests follow-up for each reviewed item. |
| Build | Iteration and Change Monitoring | Tracks repeated revisions and helps distinguish expected refinement from defects, misunderstandings, and requests that may require change control. |
| Build | AI-Assisted Development Review | Uses AI to identify possible quality, documentation, standards, or traceability concerns for a qualified builder or peer reviewer to assess. |
| Test | UAT Approach Design | Selects how user acceptance testing will be run, including whether it is in person, remote, facilitated, independent, or hybrid. |
| Test | UAT Readiness Planning | Confirms that testers, environments, access, data, scripts, schedules, support, and entry conditions are ready before testing begins. |
| Test | Test Plan | Defines what will be tested, how testing will be managed, who is responsible, what evidence is required, and how the phase will exit. |
| Test | UAT Test Script Generation | Creates step-by-step business tests from approved requirements, designs, processes, roles, and risks. |
| Test | Coverage Analysis | Shows whether approved requirements, business processes, roles, scenarios, and major risks are adequately represented in the test set. |
| Test | Test Data Preparation | Defines and prepares the records, starting conditions, expected values, and reset steps needed to execute each test. |
| Test | Tester Guidance | Gives testers clear instructions for accessing the solution, running tests, recording evidence, reporting problems, and obtaining help. |
| Test | Test Execution Tracking | Tracks which tests are assigned, started, passed, failed, blocked, incomplete, or ready for retest. |
| Test | Defect Intake and Classification | Captures reported problems and separates true defects from questions, data issues, training needs, and enhancement requests. |
| Test | Duplicate-Defect Detection | Identifies reports that may describe the same underlying problem so the test team can avoid duplicate investigation and tracking. |
| Test | Test and Enhancement Log | Maintains the reviewed list of defects, enhancements, decisions, priorities, owners, target dates, and current dispositions. |
| Test | Defect Triage and Summary | Assesses each defect's severity, business impact, affected requirements, likely cause, priority, and required action. |
| Test | Retest and Regression Planning | Identifies which failed tests must be rerun and which related functions should be retested after a change. |
| Test | UAT Measurement | Measures participation, test execution, defects, retesting, and readiness in a way that fits the selected UAT operating model. |
| Test | Test Exit Assessment | Compares testing evidence with the approved exit criteria and presents remaining risks and exceptions for a human readiness decision. |
| Test | Sign-Off Package | Assembles test results, evidence, unresolved exceptions, accepted risks, and approvals for formal business sign-off. |
| Train | Training Scope and Audience Plan | Defines who must be trained, what each audience must learn, which formats and materials are included, and who owns delivery. |
| Train | Administrator Training | Prepares designated administrators to operate, govern, maintain, troubleshoot, and support the solution. |
| Train | Model Builder Training | Teaches qualified builders how the model is structured, configured, maintained, and governed. |
| Train | Train-the-Trainer | Prepares client trainers to deliver consistent training using approved content, exercises, facilitation guidance, and support materials. |
| Train | End-User Training | Teaches business users how to complete the processes and decisions for which they are responsible in the new solution. |
| Train | Training Material Generation | Produces draft guides, job aids, exercises, facilitator scripts, presentation content, and reference materials from the approved solution. |
| Train | AI Training Video Production | Creates draft video scripts, narration, scene plans, and demonstrations that can be reviewed and produced as on-demand learning. |
| Train | Administrative Runbooks | Documents repeatable administrative procedures, controls, troubleshooting steps, ownership, and escalation paths. |
| Train | Content-to-Solution Validation | Checks that training materials match the current approved solution and identifies content made outdated by design or build changes. |
| Train | Training Schedule and Dependency Management | Coordinates training dates and prerequisites with build completion, testing, deployment, environment access, and content readiness. |
| Train | Training Readiness Review | Confirms that trainers, audiences, materials, environments, communications, and prerequisites are ready before training begins. |
| Train | Learning Completion and Feedback | Tracks attendance, completion, learner feedback, knowledge gaps, and follow-up actions by audience. |
| Deploy | Deployment Planning | Defines the go-live activities, sequence, responsibilities, dependencies, communications, contingencies, and decision points. |
| Deploy | Cutover Readiness | Confirms that data, integrations, security, environments, support, communications, validation, and rollback plans are ready for cutover. |
| Deploy | Go-Live Decision Package | Presents the readiness evidence, unresolved risks, exceptions, ownership, and recommendation needed for an authorized go-live decision. |
| Deploy | Release Communications | Prepares reviewed messages that explain the release, timing, user impact, required actions, support channels, and known limitations. |
| Deploy | Production Validation | Confirms immediately after deployment that the production solution, data, access, integrations, and critical processes operate as expected. |
| Deploy | Project Closeout | Confirms that deliverables, approvals, documentation, contractual obligations, financial actions, and outstanding ownership have been addressed. |
| Deploy | Decision and RAID Closure | Closes, transfers, defers, or assigns ongoing ownership for remaining decisions, risks, assumptions, issues, and dependencies. |
| Deploy | Lessons Learned | Captures what worked, what did not, what should change, and what Karta can reuse on future engagements. |
| Deploy | Final Client Handoff | Provides the client with the approved solution artifacts, operating documentation, responsibilities, open items, and roadmap recommendations. |
| Deploy | Hypercare Planning | Defines whether hypercare is included and establishes its services, duration, staffing, measures, communications, entry criteria, and exit criteria. |
| Deploy | Hypercare Management | Coordinates rapid issue intake, triage, resolution, communication, trend analysis, and stabilization during the post-launch support period. |
| Deploy | Hypercare Exit Assessment | Evaluates whether the solution is stable, open issues are controlled, and ownership can move from the project team to Continuous Support. |
| Continuous Support | Support Handover | Transfers the approved solution history, architecture, runbooks, stakeholders, access, decisions, known limitations, and open work to the support team. |
| Continuous Support | Receiving-Team Acceptance | Records that the Continuous Support owner has reviewed the handover, resolved material gaps, and accepted ongoing responsibility. |
| Continuous Support | Open-Item Transition | Assigns clear ownership and treatment for defects, risks, deferred scope, enhancement requests, and other work remaining after implementation. |
| Continuous Support | Service Model Setup | Defines support hours, service levels, severity definitions, intake routes, responsibilities, escalation paths, and communication expectations. |
| Continuous Support | Request Classification | Determines whether an incoming request is an incident, defect, service request, question, data issue, or enhancement. |
| Continuous Support | Issue Triage and Resolution | Assesses impact and priority, assigns ownership, coordinates investigation and resolution, and records evidence before closure. |
| Continuous Support | Recurring-Issue Analysis | Identifies repeated problems, likely root causes, systemic risks, and preventive improvements across support activity. |
| Continuous Support | Solution-Health Monitoring | Monitors available reliability, usage, adoption, data-quality, performance, and service indicators to identify conditions needing attention. |
| Continuous Support | Enhancement Backlog | Maintains requested improvements with their business value, scope, priority, effort, dependencies, decision status, and release target. |
| Continuous Support | Release and Regression Support | Plans support releases and identifies the validation and regression testing required before production deployment. |
| Continuous Support | Value and Roadmap Review | Uses support evidence, adoption results, business priorities, and enhancement opportunities to recommend the next solution investments. |
| Continuous Support | Continuous-Improvement Feedback | Converts reusable support lessons and recurring quality patterns into proposed updates to Karta methods, standards, examples, and training. |
| Cross-Phase Workflows | Engagement Home | Gives the team one place to see the current lifecycle position, dates, parallel workstreams, obligations, recent activity, and recommended actions. |
| Cross-Phase Workflows | Project Chat | Answers project questions using authorized sources and approved engagement records while showing supporting evidence and known gaps. |
| Cross-Phase Workflows | Weekly Status | Guides the team from source review through narrative drafting, approval, and production of the recurring project status deck. |
| Cross-Phase Workflows | Decision Log | Preserves what was decided, why it was decided, who approved it, when it took effect, and what project work it affects. |
| Cross-Phase Workflows | RAID Management | Maintains the project's risks, assumptions, issues, and dependencies with ratings, owners, actions, due dates, and current status. |
| Cross-Phase Workflows | Delivery Traceability | Connects scope, requirements, design, build, tests, training, deployment, and support so coverage and change impact can be understood. |
| Cross-Phase Workflows | Change Control | Routes material scope, schedule, budget, or solution changes through documented impact analysis and authorized approval. |
| Cross-Phase Workflows | Artifact Library | Provides controlled access to current and historical drafts, approvals, source links, and versions of project deliverables. |
| Cross-Phase Workflows | Delivery Insights | Identifies evidence-based conditions that may require action, such as schedule risk, scope drift, quality gaps, capacity concerns, or readiness issues. |
| Cross-Phase Workflows | Team Onboarding and Development | Provides role-specific project context, approved examples, Karta guidance, and learning support for new and junior team members. |
| Cross-Phase Workflows | Capability Catalog | Shows which AI capabilities are available, planned, experimental, or restricted and explains how each may be used safely. |
